# Task M2-018: Implement HLT

## Summary

Добавлена atomic HLT execution и minimal halted guard. HLT latch-ит `HALT_STATE`, а последующие `step()` calls возвращают без fetch или architectural mutation до reset.

## Scope

В scope входят HLT execution, minimal `step()` halted guard, no-fetch behavior after HALT, reset interaction и policy independence. Canonical control-word HLT entry, edge timing, MICROSTEP hold, clock blocking, halt reason и full dispatcher не реализуются.

## Design decision

`ArchitecturalState.execute_instruction()` получил ветку `Opcode.HLT`, которая вызывает existing `HaltLatch.latch()` и возвращает `None`.

Добавлен минимальный orchestration boundary:

```text
step()
  if HALT_STATE: return None
  instruction = fetch_instruction()
  return execute_instruction(instruction, policy=policy)
```

Этот boundary проверяет halted behavior для текущих supported instructions и не является complete M2-020 dispatcher/result abstraction.

## State preservation

После HLT сохраняются A, post-fetch PC, IR, SRAM, concrete FLAGS и `flags_defined_mask`; устанавливается только HALT state. При halted guard fetch не выполняется, поэтому PC/IR/SRAM/instruction effects не изменяются. Reset очищает HALT, восстанавливает обычное architectural state и сохраняет SRAM.

## Policy behavior

HLT не читает FLAGS, не вызывает policy resolution и не создаёт diagnostic. Optional `STRICT`/`HARDWARE_LIKE` input не влияет на HLT behavior.
